## 场景结构

没有按原来的「多个 GameObject 分工」做。实际是**一个空场景 + 一个挂 `Bootstrap` 的物体**，其余全部在运行时用 `AddComponent` 装上去（`Assets/Editor/AutoScene.cs` 负责生成这个空场景）：

- `Bootstrap`：入口，建逻辑、建视图、接相机、订阅事件，也收命令行调试开关（`-auto`、`-size X Y Z`、`-fluidtest`、`-sandtest`、`-blocktest` 等）
- `GameLoop`：纯 C# 类，不继承 MonoBehaviour，状态机与主循环
- `GridView` / `ParticleBurst` / `Hud` / `TitleScreen` / `NextPreview` / `SfxPlayer` / `KeyboardInput` / `CameraRig`：都是运行时挂上的组件
- `GridFrame`：挂在独立子物体上（它 `Build` 时会清空自己的子节点，和 GridView 同物体的话会把格子删掉）

之所以这么散，是为了让逻辑层（`GameLoop` / `Grid` / `Gravity` / `Fluids`）完全不碰 `MonoBehaviour`，可以在批处理里直接 `new` 出来跑自检。

## 数据模型

- 场地用三维 `int[x, y, z]` 存（`Core/Grid.cs`），`0` 是空，`> 0` 是 `BlockCatalog.Blocks` 的下标 + 1
- 方块形状用 `Vector2Int[]` 描述四个格子（方块本地 x-y 平面里的 `1×4` / `2×2` 形状），**形状永远不动**，怎么摆由朝向决定
- 朝向是 `PieceRotation`：一个整数 3×3 旋转矩阵（元素只有 -1/0/1，共 24 种），三根列向量 = 本地 x/y/z 轴在世界里的指向
- `Piece.WorldCell(i)` = 原点 + `CellOffset(i)`；`CellOffset` = 朝向矩阵乘上平面格坐标，再整体平移到非负（原点永远是包围盒最小角）。三组旋转键都只改朝向，谁也踩不着谁
- 方块类型：平面 7 种 I、O、T、S、Z、J、L，立体块未做
- 方块外观按 `BlockId` 查 `BlockCatalog`：六面各指向图集里一个格子，另带放置音效分组名（MC 的 SoundType）和是否透明
- **流体单独存**，不占网格：`Fluids` 内部两张 `int[x,y,z]`——份数（0~8）和流体种类（水 / 岩浆）。详见「MC 效果」章节

## 坐标与方向

- y 轴是下落方向，0 在底部
- 场地边界由设置里的 x、y、z 决定
- 相机看向场地中心

## 旋转

三组键，对应屏幕上的三根轴，互不干扰、可以任意叠加：

| 键 | 轴 | 效果 |
|---|---|---|
| Q / E | 屏幕法线（z） | 面内旋转，方块始终正对玩家，和经典俄罗斯方块一致 |
| Z / C | 竖直轴（y） | 俯视旋转，整块转过去朝别的方向 |
| R / V | 水平轴（x） | 前后翻：往背面倒 / 往正面翻 |

**为什么存矩阵而不是三个角度**：绕世界轴的旋转不满足交换律。用「偏航 + 俯仰 + 翻滚」三个数分开存，
先绕 y 转再绕 x 转，结果就不是 `(yaw, pitch)` 能表示的形状了；而且转到 90° 会撞 gimbal lock，
两组不同的角度指向同一个朝向，再转一下就分叉。存整数矩阵没有这个问题——每次按键都是
「左乘一个 90° 基本旋转」，先按哪个键都对得上，24 种朝向一一对应立方体旋转群，
还能拿三进制压成一个 int 存档（`PieceRotation.Code`）。

**三个基本旋转的方向是实测的**，不是按手性推的（推错一次就会让"看起来转了、碰撞没转"）：

- `Euler(0,0,-90)`：right → -y、up → +x
- `Euler(0,-90,0)`：right → +z、forward → -x
- `Euler(90,0,0)`：up → +z、forward → -y（+z 是画面深处，所以这就是"往背面翻"）

**转完要重新找落点**：绕轴转 90°，方块在那两根轴上的包围盒会变（宽 w ↔ 厚 w、躺平 / 竖起来），
所以 `TryRotateAbout` 统一做这几步：

1. 记下转之前整块占据的绝对包围盒（`min+max`，省掉取整误差）；
2. 换朝向，算出转之后（原点当 0）的包围盒；
3. 让新旧包围盒在**变化了的那两根轴**上中心重合，得到目标原点。面内旋转例外：
   不对齐、原点不动——宽 I 贴着地转成竖 I 时它会从原位置往上长，这才是俄罗斯方块的手感，
   对齐中心反而会往下沉进地里；
4. 转不下就往四周挪 1~2 格，最后试着抬 1~2 格（往上踢墙）；全不行就还原朝向、静默返回 false。

场地 z 只有 1 格时，俯视旋转和前后翻必然失败（转过去至少需要 z ≥ 2，I 型要 4 格）。
这是设计上的正常结果，不是 bug。

**视图层**：`GridView` 每帧从 `Piece.Rot.ToQuaternion()` 取目标朝向做 `Slerp`，不做角度累加——
三组键怎么按都不会累积误差，同帧内"转完立刻硬降"也能拿到正确角度。落定时按同一份四元数
写给每一格（`SetCellRotation`），否则落定瞬间方块会「啪」地翻回去。流体是例外：水是矮方块，
任何角度都会让它立起来变成竖切片，所以流体格子一律 identity。

**注意**：平面方块只有 1 格厚，所以绕 x 轴翻 90° 后，"1×1 截面"的那条 I 型看起来形状没变
（只转了贴图方向），3 宽 2 高的 T / J / L 才会明显躺平。这是几何上的必然，不是没生效。

## 游戏循环## 游戏循环

状态机：主菜单 → 游戏中 → 暂停 → 结束

游戏中每一帧：

1. 读输入
2. 推进流体（`Fluids.Tick`：先做水岩浆反应，再做流动，见下文）
3. 当前方块按重力下移一格
4. 碰撞检测，撞了就锁定
5. 锁定后结算：写网格 → 挤走被压住的流体 → 重力方块塌落 → 检查消除、执行消除、上方下落
6. 结算后派事件给视图层（粒子、滑落动画、音效）
7. 需要时生成下一块

注意第 5 步里前三小步的顺序不能换，理由写在「MC 效果」章节。

## 消除

- 行消：遍历所有 (y, z) 组合，某一行 x 方向全部填满就消
- 层消：遍历所有 y，某个高度层的 x × z 全部填满就消
- 消除后上方整体下落补位

两种模式在设置里切换，规则逻辑各自独立，别写成一个带分支的大函数。

## MC 效果

原来打算定义 `IBlockEffect` 加四个空实现，把效果做成可插拔的。实际做的时候放弃了：沙子必须在「写网格之后、判满行之前」这个精确位置跑，流体还要和 `Grid` 双向通信（注入满行判定、消行时回调清水），套一层接口只是把顺序关系藏起来，反而更容易写错。

现在两个效果各是一个静态类，直接在 `GameLoop` 里按固定顺序调用，调用点本身就是文档。

### 重力方块：`Core/Gravity.cs`

- **谁掉**：`IsFalling(blockId)` 拿 `BlockCatalog` 里的英文名判断——`sand`、`red_sand`、`gravel`、`suspicious_*`、`*_concrete_powder`。用名字而不是编号，是因为方块表由工具生成、编号会变。
- **怎么掉**：`Settle` 从下往上扫，能往下就挪一格，重复最多 `SizeY + 2` 趟直到全场不动。多趟是因为一柱沙子要连续塌。
- **给视图**：每挪一步记一条 `GravityStep{From,To}`，调用方传 `List` 进去就拿得到；视图按 To 的 y 升序搬显示对象，看起来是滑落而不是瞬移。
- **调用位置**：`GameLoop.LockPiece` 里，写网格和挤流体都做完之后、判满行之前。顺序理由：刚落下的沙子可能正好补满一行，先判满行就漏消了。

### 水与岩浆：`Core/Fluids.cs`

**数据**：水不写进 `Grid`。`Fluids` 自己维护两张同尺寸的 `int[x,y,z]`——`_amount` 记每格几份，`_id` 记是水还是岩浆。

- 一格最多 `MaxAmount = 8` 份，8 份 = 满格 = MC 里的「源」，之后按份数递减就是「流动」。
- 不写网格的三个理由：水不能当碰撞体挡住方块；写进去会和流体数组重复记录，渲染出两份水（体积凭空翻倍）；方块压过水时只需要搬流体，不用改网格。

**流动**（`Step`，每 0.1 秒一次）：

1. 从下往上扫每一格。
2. 正下方不是方块 → 往下方剩余空间灌，灌满后剩下的留在本格。这样上下叠着的几片 1/8 会并成一柱，而不是每层各留一片薄水。
3. 只有「已经落到底」的那层（下方是方块或已触底）才往四个侧面摊。
4. 侧面吸附：邻居最多涨到本格的一半，一个 tick 只给 1 份。所以水是慢慢渗开的，边上的薄水会停在原地，不会一次摊平。

总份数在整个过程中守恒，这是这个模型的核心约束。

**被方块压住**（`OnSolidPlaced`）：方块落定时如果那一格有水，把那格水往上搬——和上方原有的水合成一滴，装满一格再往上一格，上方全满才试四个侧面，四处都满才丢掉。往上找的是「网格里是空的」第一个格子，因为竖着落下的 I 形自己就占着 y+1。

**和 Grid 的双向连接**：`Grid` 里留了两个可注入的委托，`Bootstrap` 在 `Start` 里接上。

- `Grid.CountsAsFilled` → 水量满 8 份就算这格有东西，能跟方块一起凑满一行。
- `Grid.OnCellCleared` → 消行时把那一格的水一起清掉。

**渲染**：`GridView` 给每种流体预建 9 档高度的 mesh（1/8 到 8/8），按当前格份数选一档。份数是每格自己的，不参考上下的水——以前按「上面压着水就画满格」会把 3 个 1/8 拼成一个满格，看起来像水凭空变多。

流体格子不吃旋转。落定时 `SetCellRotation` 会把方块的朝向写给每一格，正方体转了看不出来，但水是矮方块——只要带上一点面内角度（roll），1/8 的水就会从「一片水面」立成「一片竖墙」，屏幕上是一道半透明的薄切片。所以 `GridView.CellRotation(isFluid, yaw, roll)` 对流体的 roll 一律归零，只留绕竖直轴的 yaw（水面形状不变，顶面纹理跟着转）。`SetCell` 画流体时也会把旋转重置成 identity，免得这一格之前装过别的方块、留着旧角度。

**水岩浆反应**（`React`，每个 tick 在 `Step` 之前跑一次）：

- 扫所有岩浆格（`_id == LavaId` 且份数 > 0），看六向邻居里有没有水。
- 有就结晶：份数满 8 的变 `obsidian`，不满的变 `cobblestone`，写进 `Grid`，同时把该格流体清空；参与反应的那一格水整格清掉。
- 同一格里同时有两种流体（水方块落进岩浆格）也当场结晶，逻辑在 `AddSource` 里：不做这一步的话，后落的流体会把先落的覆盖掉，垂直相遇就永远看不到石头。
- 每条反应记进 `LastReactions`（产物坐标 + 方块编号 + 水格坐标），`GameLoop` 读到后派 `FluidReacted` 事件，`Bootstrap` 用它刷新那几格并播音效、撒碎屑。
- 先反应再流动，所以这一 tick 新生成的石头立刻能挡水。连锁就是自然结果：水吃不到的地方靠下一 tick 流动再补上，看起来是逐块结块，不会一次全反应完。
- 产物编号在 `Fluids.Init()` 里按名字查一次缓存（`ObsidianId` / `CobbleId`），查不到就退化成不反应，不抛异常。

**音效**：`random.fizz`（水浇灭岩浆的嘶声）。已用 `tools/extract_sound.py random/fizz fizz` 从 26.2 的资源库提取到 `Assets/Resources/Sfx/fizz.ogg`，由 `SfxPlayer.PlayFizz` 播；万一素材丢了会退回放置石头的声音。

### TNT：`Core/Tnt.cs`

**怎么点火**：TNT 六向（含同格）挨着红石块或岩浆就点着，和 MC 一致。

- 判定放在 `LockPiece` 的**最后**（消行之后、`SpawnNext` 之前），每次落定全场扫一遍。
  扫全场而不是只看刚落下的那几格：接触可能是新放的红石凑上旧 TNT，也可能是新放的 TNT 凑上旧红石，
  重力塌落之后位置还会变，逐个追来源不如一次扫 2000 格（10×20×10）省事，也不慢。
- 扫在消行之后是因为消行会把整排往下挪。先点火再消行，记下的坐标就指到别处去了。
- **岩浆**不写网格（走 `Fluids` 的份数模型），网格里那一格是空的，所以判定要额外查
  `Fluids.AmountAt > 0 && Fluids.IdAt == Fluids.LavaId`。也因为它不占网格，
  落定那一次扫描看不见它漫过来的过程，`GameLoop.Tick` 在 `Fluids.Tick` 返回「有变化」时
  再调一次 `PrimeContact`，让岩浆淌到 TNT 旁边当场点着。水不点（只认岩浆）。

**引信**：`FuseSeconds = 2.4`（原版 4 秒，一局俄罗斯方块里太长）。燃烧期间方块**留在网格里**原地闪。

- 留网格的代价是「被消行带走时会哑火」；好处是坐标不会因为重力 / 消行错位。
- 所以 `Tick` 每帧验一次「这一格还是 TNT 吗」，不是就静静丢掉这颗。
  如果它只是被挪走了，下一次落定时 `PrimeContact` 还会再扫到它，等于自动重新点火。

**爆炸**：球形判距离，`BlastRadius = 2.0`。

- z = 1 的场地上只有 `dz = 0` 一层穿过球心，实际是半径 2 的圆，约 13 格；
  场地深到 z ≥ 2 才炸出完整的一团。
- 顺带把范围内的水 / 岩浆吹掉（否则会从弹坑里流回来，看起来像没炸开）。
- 炸到的 TNT 不直接消失，而是点着（0.18 ~ 0.55 秒短引信），形成连锁。
- 爆心那格要特判清掉：不特判它自己会走「邻居是 TNT」那条分支把自己又点一次。
- **原版 TNT 炸不掉的方块也炸不掉**：基岩、三种命令方块、黑曜石、哭泣的黑曜石、
  远古残骸、下界合金块、强化深板岩。这九种在原版的爆炸抗性是 3600000 或 1200，
  而 TNT 的爆炸威力只有 4，所以原版也炸不动它们。判定放在
  `BlockCatalog.IsBlastProof(blockId)`（按名字查表，懒加载一次）。
  命中的格子原样保留：不进 `blast.Cells`，所以既不炸碎也不计分（炸掉一格 4 分的账只算真炸掉的）。
  流体是另一回事：空格里的水 / 岩浆照旧被吹掉（原版 TNT 能把水炸开）。
- **结构方块不进这张表**：原版抗性也是 3600000，但这里的结构方块靠「被炸掉」触发还原，
  列进来就把它的触发点砍掉一个。这条是设计上的故意偏离，记在设计规格里。

**爆炸之后的连锁账**：`GameLoop.Tick` 里读完 `LastBlasts` 要接着跑一次 `Gravity.Settle`——
弹坑上方的沙子 / 沙砾得塌下来，不然会浮在半空。分数按炸掉的格子算（`ScorePerBlock = 4`，
清一行是 100，炸一圈差不多半行的收益）。

**表现**：`SfxPlayer.PlayFuse`（`random.fuse`）+ `PlayExplode`（`random.explode1~4` 随机）、
`CameraRig.Shake(0.6f)` 震屏、`ParticleBurst.EmitCell` 抽样撒碎块（一次能掀几十格，
按步长抽样封顶约 24 格，不然粒子池直接爆）。

**闪白**：`GridView.SetCellFlash` 把那一格的材质换成纯白（克隆 `BorderMat`，也就是 `Unlit/Color`）。

- 为什么克隆材质而不是 `Shader.Find("Unlit/Color")`：构建版里没有任何资源引用的 shader 会被裁掉，
  `BorderMat` 是 Resources 里的资源、引用了它，所以那个 shader 一定在包里。
- `SetCell` 重建材质时也要判一次闪白标记，否则 `RefreshAll` 一跑白闪就丢；
  同时顺手把「这一格已经不是 TNT」的旧标记清掉，不然下一块落到这里会莫名其妙是白的。
- 闪白频率照抄原版：MC 的 `TntRenderer` 用引信 tick 数算 `fuse / 5 % 2`，每 5 tick 换一次贴图，
  也就是 0.25 秒白 / 0.25 秒原色（2 Hz 方波）。`Bootstrap.SyncTntFlash` 用「已经烧了多久 ÷ 0.25」
  算相位，每帧把 `Tnt.PrimedCells` 同步给视图。相位跟引信走而不是跟全局时钟走，
  连锁点着的几颗才各自错开，不会全场同时闪。

**怎么拿到 TNT**：`BlockPools` 里 TNT 不进普通池，而是当作道具放在特殊池里占 20%
（水 30% / 岩浆 20% / TNT 20% / 沙类 30%，每 12 个方块抽一次特殊池）。
抽到 TNT 之后**下一次抽必定给红石块**（`_forceRedstone`）——只给 TNT 不给红石的话，
红石块在三百多分之一的普通池里，这个机制基本等于不存在。

### 原木长树叶：`Core/Foliage.cs`

原版里原木不会长树叶（树是世界生成时整棵一起出现的），这条是本项目的自创规则。

- **认谁**：名字以 `_log` / `_wood` 结尾的方块。`stripped_*`（剥皮）不长，菌柄 / 菌核
  （`_stem` / `_hyphae`）不长——菌类没有树叶；`bamboo_block` 不长。
- **长什么**：同树种的 `<木头>_leaves`，`oak_log` → `oak_leaves`。映射在 `Init()` 里按名字建一次表，
  查的时候是一次数组访问（方块编号 → 树叶编号）。
- **长哪**：正上方、斜上方一圈 8 个、同层四个侧面，共 13 个候选位；要求那格是空的、且没有积水。
  候选里随机挑一个——固定按顺序取第一个的话，叶子永远朝同一个方向长，看着像贴上去的。
- **上限**：一个原木格长一片，一次落定最多 6 片（`MaxLeavesPerLock`）。创意工坊里画个 16 格的原木模具，
  不该一次刷出 16 片叶子。
- **时机**：`LockPiece` 里，重力结算之后、判满行之前。放在消行之前是有意的：树叶补满的行当场就消，
  否则那行要等下一块落定才消，看起来像卡住了。
- 树叶是普通方块：进网格、挡方块、能凑满行、能被消除、跟着存档走。不做原版的「没有原木就枯萎」。
- 树叶走透明材质（`BlockTransparentMat`，`clip(a - 0.01)` 挖孔），所以 `IsTransparent` 里判的就是名字带 `leaves`。

**这批树叶方块是新加进方块表的**（原来 342 种里一个树叶都没有：`scan_full_blocks.py` 的
`EXCLUDE_WORDS` 就把 leaves 排除了，因为它们是 cutout 渲染）。补的时候有三个约束：

1. **只能追加到末尾**。方块编号就是数组下标，插在中间会让所有后续方块编号平移，老存档的网格全变成别的方块。
   所以 `scan_full_blocks.py` 里加了 `EXTRA_BLOCKS`（当时叫 LEAF_BLOCKS，后来加基岩时改了名），扫完追加；`build_full_atlas.py` 里贴图也是按方块顺序收集，
   新贴图自然排在最后——421 个旧格子一个像素都没动（可用 `ImageChops.difference` 验证差异只在最后 9 格）。
2. **灰度贴图要染色**。oak / spruce / birch / jungle / acacia / dark_oak / mangrove 的树叶贴图是灰度的，
   原版靠 biome 的 foliage 色上色；不染的话树叶是灰白的。樱花和苍白橡树的贴图本身带色，不染。
3. **放置音要单独给规则**。树叶在原版是 SoundType.GRASS，`build_place_sfx.py` 的规则表里加了
   `.*_leaves → grass`；不加会落到兜底的 stone，踩到树叶响成石头。

### 基岩不随消除下落

原版里基岩是不可破坏的，消行时也不会跟着掉。这里取了个折中：**消除时钉在原地不动，
但自己所在的行被消掉时照样消失**——算是「可以被消除」。

**改动点在 `Grid` 的下落算法**，不在玩法层：

- 原来消行是「把上一行整体搬下来覆盖当前行」（`DropRowAbove` / `DropLayerAbove`）。
  碰到基岩有两个问题：基岩被一起搬走（它该钉住），基岩上方的方块又会直接穿过它掉下来（它该被托住）。
- 改成**逐格判断「下面那格空不空」**：基岩自己不落（它占着格子），上方那一摞就自然停在它上面。
  从下往上扫，先落低的，高的那一格才看得见刚空出来的位置。
- 关键细节：被消的那一行**必须先自己清空**。原来的写法是靠「搬下来覆盖」顺手清掉的，
  换成逐格下落之后没有东西覆盖了，不清的话 `while (IsRowFull(y))` 会永远转下去（这个坑踩过一次，
  自检直接报 OutOfMemoryException）。

**后果**：基岩钉住的那一列，消行后会**永久留一个洞**（基岩下方那格空着）。
那一列从此填不满满行，是这个规则的必然结果，也是它「钉住」的代价。

**谁算锚点**：`BlockCatalog.IsAnchor(blockId)`，目前只有基岩。编号在 `BlockCatalog.BedrockId`，
按名字查一次建表，运行期是一次数组访问。

**怎么拿到基岩**：常驻特殊池，占特殊池的 12%（约 1% 的方块是基岩）。
设置里的「基岩钉住不动」关掉之后，`IsAnchor` 直接返回 false，基岩就成一块普通砖。
开关存在 PlayerPrefs，改完立即生效，不重建池子（方块本来就在池里）。

**基岩方块是新加进方块表的**（和树叶一样，`scan_full_blocks.py` 的 `EXCLUDE_WORDS` 里就写着
`bedrock`）。所以 `LEAF_BLOCKS` 改名成 `EXTRA_BLOCKS`，末尾追加基岩，编号 351 → 352，
旧编号一个没动。玻璃同理追加在基岩之后（352 → 353），旧编号也不动。

### 结构方块的记忆与还原：`Core/Structure.cs`

原版的结构方块能存一整个结构，本项目简化成：**落定时记住整块场地，被消掉时还原回来**。
2026-10-28 晚把范围从中心 3×3×3 改成整场，一整块方块只记一条；
当天再晚一点又把还原动画从「一波扫过去」改成两段：先一格一格收掉，再一格一格掉回来。

**记忆**（`RememberCells` / `RememberFromPiece`）

- 触发在 `GameLoop.LockPiece` 里方块写进网格之后、`Gravity.Settle` 之前。
  整块方块是同一个 id，一块里可能有 4 格结构方块；这 4 格来自同一次落定，
  只记一条记忆（`Memory.Cells` 存下它们，3 个一组），任意一格被消掉就触发一次。
- 范围是整块场地（`Memory.SizeX × SizeY × SizeZ`），快照存下每一格方块 id，不含流体。
- 同一格上又落了一块结构方块，说明旧的那块早没了，旧记忆直接作废（`ForgetAt`）。
  记一次就顶掉旧的那条，记忆表不会被触发不了的旧快照填满。

**还原**（`Trigger` → `Tick`）

- 触发点有三处，都必须在**那一格被搬走 / 清掉之前**判断，否则读不到它原本是什么：
  `Grid.ClearFullRows` / `ClearFullLayers`（消行）、`Tnt.Explode`（爆炸）。
- 流程分两段，都是「从下往上、一个接一个」：
  1. **消失**（`Phase.Clear`）：`BeginRestore` 把这条记忆里结构方块占的格子记成空的
     （它是这次还原的开关），再扫一遍记忆范围，把现在有东西的格子从下往上排成一张清单。
     每 `ClearInterval = 0.035` 秒收掉一格：清方块、清流体、发 `CellVanished`（视图擦掉那一格，
     再撒一点碎块）。收完再查一次场上还有没有东西（消失的这一两秒里玩家可能又落了一块），
     有就再收一轮。
  2. **重建**（`Phase.Drop`）：把快照里有方块的格子从下往上排成清单，每 `DropInterval = 0.05`
     秒落一格：写回网格、发 `CellDropped`。视图层 `GridView.SetCellDropping` 把这一格的视觉位置
     先放到目标上方 `DropHeight = 2` 格，`Update` 里的插值把它掉下来。
  3. **收尾**：重建走完，删掉这条记忆，发 `Finished`。
- **两段各封顶 `MaxPhaseTime = 3` 秒**：`BatchFor` 按格子数算一次处理几格。
  8000 格的场地也不会演几十秒。
- **收尾时不要再擦一遍格子**：第一版想过在 `Finish` 里把结构方块那几格再清一次，
  但还原要跑几秒，玩家完全可能在这期间把新方块放到那几格上，收尾一擦就把它删了。
  结构方块自己已经在消失阶段收掉，这一步没必要。
- 一次只还原一个，同时触发多个就排队（`Queue<Memory>`）。等待中的记忆如果它的结构方块
  被前一个还原收掉，会被标成 `Cancelled`，出队时跳过。

**还原时的连带清理**

- 消失阶段收掉某格时，如果那格立着别的结构方块，说明这块结构方块在这次还原里被抹掉了，
  记在它上面的记忆作废（正在还原的那条除外）。不清理的话，记忆表里会积累
  永远触发不了的快照，存档也跟着变大。

**存档**

- `SaveData` 加了 `structures` 字段，记忆拍平成 int 数组。第一个数是版本标记 `-2`，然后每条：
  11 个头（中心 3 + 范围起点 3 + 尺寸 3 + 块数 1 + 格子数 1），接着是块 id，
  最后是这块结构方块占的格子（3 个一组）。
- **版本标记**：老存档没有前缀，第一个数是中心 X（≥ 0），不会和 `-2` 撞上。
  读到老格式就按 3×3×3 那套读，格子只有中心一格。
- **范围起点必须一起存**：老记忆的范围是「中心 ±1 再裁到场地内」，贴边时尺寸会变成 2，
  光靠中心和尺寸反推起点会算错半格。
- **格子必须一起存**：一块 4 格结构方块只记一条，光有锚点找不到另外三格。

**配比**：常驻特殊池，占 10%（特殊池改成累加式分配之后就是固定那份）。
设置里的「结构方块还原」关掉之后，`RememberFromPiece` / `NotifyCleared` / `Tick` 全部早退，
方块照样进池、照样能消，只是不记事、不还原。

### 玻璃被压碎：`Core/Glass.cs`

**玻璃正上方那一格有方块，这格玻璃就碎。**

- 判定是一遍场地扫描：`Glass.Crush(grid, outCells)` 从 y = 0 扫到 `SizeY - 2`
  （最上面一层上面不可能有方块），某格是玻璃且 `grid.Get(x, y + 1, z) > 0` 就清掉、记进清单。
- **不在每条落地路径上埋判定**：方块落到玻璃上的来源有落定、重力、行消下移、层消下移、
  结构方块还原五处，逐个埋点总会漏一条；默认 200 格扫一遍比维护五处判定便宜。
- **调用点**：`GameLoop.LockPiece` 里 `Foliage.Grow` 之后、判满行之前，`CrushGlass()`。
  放在判满行之前，是因为玻璃碎了上面的沙会接着掉，掉下来的方块可能正好补满一行。
- `CrushGlass` 是一个循环：碎一轮 → `Gravity.Settle` → 再碎一轮，直到没有玻璃再碎（上限 64 轮），
  这样叠着几层玻璃会一层层塌下去。每轮的重力位移照常发 `GravitySettled`。
- 事件：`GameLoop.GlassCrushed`（碎完发一次，格子清单在 `LastGlassCrushed`）。
  `Bootstrap.OnGlassCrushed` 播 `Sfx/break_glass`、抖一下镜头、逐格 `_view.SetCell` 清格子、
  撒 `ParticleBurst` 碎块。
- **玻璃方块是新加进方块表的**：`scan_full_blocks.py` 的 `EXCLUDE_WORDS` 里本来就有 `glass`，
  所以加到 `EXTRA_BLOCKS` 末尾（353 号），图集重打一次，`BlockCatalog.GlassId` 按名字查。
  `BlockCatalog.IsTransparent` 里本来就有 `name.Contains("glass")`，走透明材质。
- **音效**：`build_place_sfx.py` 的 `GROUPS` 加了 `block.glass.place`、`RULES` 加了 `("glass", "glass")`；
  26.2 的 assets 索引里这个事件取不到变体，生成器退回 `dig_stone*`，所以放玻璃听起来像放石头。
  压碎那一下用的是 `break_glass`，这个是对的。

## 渲染

- 每个格子一个 Cube，材质用对应贴图
- 默认 10×20×1 是 200 个格子，对象池复用
- 可调上限 20×40×10 是 8000 个，直接铺 8000 个物体性能会掉，还没做过优化
- 方块下落用 transform 位移做，不做逐格跳动；落定后的格子在 `Update` 里朝自己的格子做指数插值，所以消行下移是「滑下来」
- 一个方块一份 mesh：`BlockMesh.Build` 按六面 UV 现拼，顶点取 ±0.52（比半格大一点），相邻方块轻微重叠，避免看到 1 像素缝
- 流体另建 9 档矮 mesh（1/8 ~ 8/8 高），见「MC 效果」

3D 版本每个方块要六面贴图。已经从 26.2.jar 里按方块模型 json 解析出来了，共 353 种方块、六面全覆盖。

## 素材导入

- 贴图全部 16×16，Filter Mode 设 Point (no filter)，压缩关掉，像素风放大不糊。
- 方块贴图打一张图集，方块各面 UV 指向图集里的格子。材质少、能合批，改某张贴图重打一次图集就行，不用动方块配置。
- 图集用脚本拼接（`tools/build_full_atlas.py`）：每格 18×18（16 像素贴图 + 1 像素复制边缘 padding），当前 353 种排成 20 × 22 格，输出 360 × 396。`npotScale` 必须设 None，否则 Unity 会把非 2 的幂贴图缩成 128×128，UV 整体错位。
- 少数贴图不直接从 jar 取：草方块顶面是灰度 tint 遮罩，生成时乘平原草色 `#91BD59`；南瓜底面原版没有，用去掉梗的顶面代替（`tools/textures/pumpkin_top_nostem.png`，走脚本里的 `LOCAL_TILES`）。
- 音效映射：
  - **方块放置：完全照 MC 原版的材质分组（SoundType）**。原版不是"一种方块一个音"，而是同一材质的方块共用一个组，组里有 3~8 个随机变体。当前 353 种方块归到 61 组，比如木板/原木 → `wood`（dig/wood1~4）、石头系 117 种 → `stone`（dig/stone1~4）、羊毛 → `wool`（dig/cloth1~4）、沙子/混凝土粉末 → `sand`、竹木 → `bamboo_wood`（音量 0.9）、压实泥 → `packed_mud`（音量 0.3）、水和岩浆 → `item.bucket.empty` / `empty_lava`（原版没有"水方块"，放下液体响的是倒桶的声音）。
  - 单行或单层消除：pickup_xp
  - 多行或多层消除：levelup
  - 界面点击：click
  - TNT：fuse 点燃、explode 爆炸（还没用上）
  - 水岩浆成石：fizz（MC 的 `random.fizz`）
- 放置音怎么来的：MC 的 ogg 不在版本 jar 里，按 sha1 存在 `.minecraft/assets/objects/<前两位>/<sha1>`，路径映射在 `assets/indexes/*.json`；**分组定义在 `assets/minecraft/sounds.json` 的 `block.<组>.place` 事件里**，事件里的 `sounds` 数组就是随机变体和各自的 volume。
  - `python tools/build_place_sfx.py` 一条命令做完：读 sounds.json → 把 281 个 ogg 拷到 `Assets/Resources/Sfx/Place/`（文件名扁平化，`dig/stone1` → `dig_stone1`，组间共用只拷一份）→ 生成 `Assets/Scripts/Core/BlockSfxData.cs`（`Groups` / `GroupClips` / `GroupVolume` / `BlockGroup`）。
  - 方块名 → 组的规则表在脚本的 `RULES` 里（顺序敏感，先具体后通用，兜底 stone）。要改某个方块的音效就加一条更靠前的规则再重跑；`--dry` 只打印分组结果不写文件，兜底接住了哪些方块会列出来，方便核对。
  - 单个音效（fizz、click 这类）还是走 `tools/extract_sound.py <资源路径> <输出名>`。

## 输入

- 没有抽 `IInputSource`。实际是 `KeyboardInput.Read()` 返回一个 `InputState` 结构（Left / Right / Up / Down / SoftDrop / HardDrop / RotateCW / RotateCCW / RotateYawCW / RotateYawCCW），`GameLoop.Tick` 只吃这个结构，所以以后加触屏只需要换一个产出 `InputState` 的类
- Windows 默认键位：
  - A / D 或 ← / →：左右移动
  - W / S 或 ↑ / ↓：前后移动（z 轴）
  - 空格：硬降
  - Shift：软降
  - Q / E：面内旋转（方块贴着玩家的那个平面里转）
  - Z / C：俯视旋转（绕竖直轴，从上往下看逆 / 顺时针）
  - Esc：暂停
- 键位自定义：每个动作存一个 KeyCode 映射，设置里改，存 PlayerPrefs，改完立即生效。实现上不依赖 Input Manager 的轴，直接用 `Input.GetKey(KeyCode)` 查映射表，运行时改键才真的有效

### 主菜单的「游戏规则」页

主菜单的按钮列表在 `UI/TitleScreen.cs` 的 `DrawButtons` 里拼，规则页挂在同一个 `SettingsPage` 枚举上
（`Guide`），面板绘制走 `DrawSettingsPanel` 的 switch。页面本体是 `DrawGuide`：先画标题、三颗切换按钮
（玩法 / 按键 / 特殊方块）和一句提示，再按 `_guideTab` 分给三个方法。

- `DrawRulesPlay`：读静态表 `PlayRules`（六段「小标题 + 正文」），一行标题一行正文，行距 P(80)，
  正文 `wordWrap = true`，两行装得下
- `DrawRulesKeys`：读 `AllActions`（12 组，和「按键设置」页同一份），两列各六行，
  左边 `ActionLabel`、右边 `KeyName(KeyboardInput.GetPrimaryKey(...))`；这里只显示，改键在设置里，
  底部两行提示改键路径和「深度 z ≥ 2 才用得上俯视旋转 / 前后翻」
- `DrawRulesBlocks`：两列每列六行（十一项，`perCol = 6`），每行 `DrawGuideRow` 画图标和两行字

三栏共用一块面板 P(1060)×P(820)，切栏时尺寸不跳；内容从 P(142) 起，最挤的是「特殊方块」栏，
行高 P(98)。加一项记得同步面板高度和 `perCol`，不然第十一项会排到面板外面。

- 图标不走 3D，直接从 `Resources/atlas` 切一格顶面：`DrawBlockIcon` 按
  `(tile.Col * CellPixels + TilePadding)` 算出像素左上角，再换算成 `Rect` 形式的 UV，

### 字体与字号缩放：`Core/UiSkin.cs`

界面字体是**方正字迹-龙吟体 简**（毛笔行书风格），放在 `Assets/Resources/Fonts/LongYinTi.ttf`，
运行时 `Resources.Load<Font>("Fonts/LongYinTi")` 取。

- **必须是动态字体**（`FontTextureCase.Dynamic` + `includeFontData = true`）：动态字体运行时按需
  光栅化，中文（含方块名里的生僻字）用到哪个渲染哪个，任意字号都清晰，也不用预生成字符集。
  `includeFontData` 忘了勾，打包后字体数据不跟着走，游戏里就是一屏方框。
  这条由 `Editor/FontImportSettings.cs`（`AssetPostprocessor`）强制保证，不靠手点 Inspector
- 字体文件用**英文名** `LongYinTi.ttf`：`Resources.Load` 的路径带中文在跨平台打包时容易出编码问题
- 字体只覆盖 GB2312 那 7374 个汉字。工程里出现过的 747 个汉字全部在覆盖范围内（`tools/inspect_font.py`
  可以重新验证）；真遇到缺字，Unity 的动态字体会自动回退到系统字体，不会变成方框
- 代价：整个 ttf 19.5 MB 会进包（`resources.assets`）。想瘦身就做子集化，但一旦有新的界面文案就得重做，
  现阶段先不折腾

字号放大用**一个系数管全局**，不是逐个数字改：

```csharp
public const float TextScale = 1.25f;          // 想更大多改这一个数
public static float P(float design);           // 设计像素 → 实际像素（布局尺寸）
public static int Size(int design);            // 设计字号 → 实际字号
```

布局里的每个像素值都过 `P()`、每个字号都过 `Size()`。**这一步不能省**：IMGUI 的字号和 `Rect`
是两套独立的数字，只放大字号 = 字变大了框没变，文字立刻被裁掉或者盖到别的控件上（这个坑踩过两次，
第二次就是下落速度页的提示文字压住按钮）。走 `P()` 之后面板和文字等比长大，`TextScale` 改成 1.5
也不会错位。

字体统一在 `OnGUI` 开头 `UiSkin.Apply()` 灌进 `GUI.skin.font`——`GUIStyle` 是 `new GUIStyle(GUI.skin.label)`
拷出来的，所以必须先设字形再建样式，否则样式拿到的是默认 Arial。

> 版权：方正字迹-龙吟体是商业字体，个人自己玩没问题，对外发布前要么买授权、要么换开源字体。

### 主菜单按钮的「目标 2 倍 + 自动降档」：`Core/MenuLayout.cs`

主菜单那摞按钮要放大，但**放大倍数不能是个定值**：标题 logo、副标题、底部署名已经吃掉一截竖直空间，
1440×900 的窗口里 6 个按钮如果真按 2 倍（每个 110px 高）算，整摞要 720px，直接越过底部署名跑到屏幕外。

所以 `UiSkin.MenuScale = 2f` 记的是**目标值**，真正的尺寸由 `MenuLayout.Compute()` 反推：

```csharp
// 在 [bandTop, bandBottom] 这条带子里，最多能放大到几倍
float byHeight = availH / unit;        // unit = n*baseH + (n-1)*baseGap
float byWidth  = maxWidth / baseWidth; // 屏宽的 86%
scale = min(targetScale, byHeight, byWidth);
```

- 拿到 `scale` 后整摞按钮在带子里**垂直居中**，`bandTop/bandBottom` 由标题、副标题、署名算出
- **字号跟着按钮一起放大**（`_menuBtnStyle.fontSize = Size(18) * scale`）。只放大按钮不放大字，
  按钮长大字没长，看起来反而更空
- 装不下时（`scale` 已被压到 0.5 下限）贴住上沿，宁可下沿顶出去也不压标题
- 实测：1440×900 五个按钮 → 1.53 倍（535×84，字 34）；六个按钮 → 1.27 倍（443×70，字 28）；
  1920×1080 五个按钮 → 1.98 倍，基本等于真 2 倍

抽成纯函数的另一个好处是**能自检**：`Compute()` 不碰 GUI，`SelfTest` 里直接喂几组屏幕尺寸断言
「总高不越界」「塞不下会自动降档」「极小窗口不会算出负数」。

配套的改动：标题从 `0.19H` 上移到 `0.15H`，副标题从固定 `0.42H` 改成**紧贴标题下方**
（原来那个位置在按钮放大后正好和新按钮打架）。

### 光标荧光拖尾：`Core/CursorTrail.cs`

深蓝色拖尾，纯 IMGUI 画，不引入任何材质 / Shader。

- 光斑贴图是**运行时生成**的一张 64×64 白色径向渐变（RGB 全白、只有 alpha 渐变，smoothstep 让边缘
  不发硬），颜色靠 `GUI.color` 染 —— 一张贴图就能画出「深蓝拖尾 + 亮蓝内芯」
- 采样放 `Update`（每帧一次），绘制只认 `EventType.Repaint`。在 `OnGUI` 里采样会因为一帧多次调用
  （Layout / Repaint）导致点数忽多忽少、形状发抖
- **按弧长补点**：鼠标一甩一帧能跑上百像素，只按采样点画就是一颗颗珠子；相邻两点之间按 0.45 个光斑
  的间距插值（上限 8 段）才是连续的彗尾
- **层级靠调用顺序，不靠 `GUI.depth`**：一开始给拖尾设了 `GUI.depth = -1000`（文档说数值越小越靠前），
  实际跑起来拖尾仍然被暂停面板的全屏压暗盖住。跨 `MonoBehaviour` 的 IMGUI 层级排序不可靠，
  于是改成「谁最后画谁来喊一声」：`Hud.OnGUI` 和 `TitleScreen.OnGUI` 在**自己最后一行**调
  `CursorTrail.DrawLast()`。同一段 `OnGUI` 里代码顺序就是绘制顺序，这条是确定的。
  用 `Time.frameCount` 做守卫，同一帧只画一次，免得两个界面都调时叠成两层发白
- 时间用 `Time.unscaledDeltaTime`：暂停时 `timeScale = 0`，用 `deltaTime` 拖尾会僵在原地
- 光斑尺寸随屏高走（`Screen.height * 0.030`），换分辨率观感一致；越老的光斑越大越淡，看起来在扩散


## 音频

**音效**：`Core/SfxPlayer.cs`。放置音按 MC 的 SoundType 分组（`BlockSfxData`，61 组 281 个变体），
每组随机挑一个录音、再叠 ±6% 音高抖动；组自带的音量（竹木 0.9、压实泥 0.3）照乘。
6 个 `AudioSource` 轮转，因为 `pitch` 挂在源上，共用一个源会把正在响的那一下也带歪。

**背景音乐**：`Core/MusicPlayer.cs`。

- **曲库**：14 首原版常速曲 + 2 首菜单曲，`tools/extract_music.py` 从本机 `assets/objects` 按 sha1 提取
  （和音效同一套索引逻辑），约 28 MB，文件名一律 ASCII。
- **随机方式**：洗牌袋（Fisher-Yates），一轮里每首各放一次，听完一轮才重洗，且重洗后第一首不会和刚放的重复。
  比 `Random.Range` 好在不会出现「连放两次同一首」。
- **静默间隔**：两首之间 10~24 秒。原版就是这个节奏，一直不停反而吵；顺带也给了流式读盘的时间。
- **淡入淡出**：开头 2.5 秒淡入，结尾 4 秒淡出。切曲库（进出标题）时也走淡出，不然会有一声爆音。
  音量包络每帧按 `min(已播/淡入, 剩余/淡出)` 算，不额外记状态。
- **两套曲库**：`Bootstrap.Update` 每帧按标题界面是否可见调 `SetMenuMode`，界面互斥、方法内部有幂等判断。
  切库时淡出当前这首、清空洗牌袋、从新曲库重新洗。
- **暂停**：`SetPaused` 走 `Pause()` / `UnPause()`。注意 `isPlaying` 在暂停时也是 false，
  所以 `Update` 里必须先判暂停再判「没在放」。
- **导入**：`Editor/AudioImportSettings.cs` 强制 `Streaming` + Vorbis + `preloadAudioData = false`。
  默认的 DecompressOnLoad 会把整首歌解码成 PCM 塞进内存（3 分钟约 30 MB），十几首就爆了。
  Unity 2022 里 `preloadAudioData` 在 `AudioImporterSampleSettings` 上，`AudioImporter` 上那个已过时（CS0619）。

## 存档

- 设置存 PlayerPrefs（场地尺寸、消除模式、下落速度、音乐音量、键位、音效开关）。下落速度单独一个页签，
  存 `fall.speed`（float），范围 (0, 2]，改完立刻生效且**不清局内存档**（它不影响局面合法性，
  和场地尺寸 / 消除模式不一样）
- 下落速度换算：`FallInterval = GameLoop.BaseFallInterval(0.8s) / FallSpeed`。倍率夹在 0.01~2.00，
  四舍五入到两位小数——下限取 0.01 而不是 0，因为 0 倍速意味着永远不掉，而 0.01 正好是
  (0, 2] 里最小的两位小数
- 最高分单独存
- 局内存档：网格 + 分数 + 行数 + 下一个方块 + 流体。流体按五元组存（x、y、z、份数、类型），读档时按五元组还原；老存档没有 `fluids` 字段就当场上没流体
- 读档前必须先 `Fluids.Prepare(Grid)` 把数组按当前尺寸建出来，`Reset` 只负责清空，不会重建

## 风险

- 8000 格上限的渲染性能
- 立体块加三轴旋转后的碰撞和旋转踢墙
- WebGL 的纹理和内存限制
- 手机触屏操作的手感
- 流体的边界情况多（被方块压、被消行带走、和存档互相影响），每加一条规则都要在 `SelfTest` 里补一条锁住
